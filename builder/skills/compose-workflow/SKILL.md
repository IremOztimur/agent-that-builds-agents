# Phase 1: compose the workflow

Read completely before designing: `docs/workflow-format.md`, `docs/tools-and-code.md`, `examples/base-agent.json`, and `.claude/skills/compose-workflow/format-rules.md` (the platform rules your workflow must follow, F = must, W = look). Follow them while you build, do not guess. Every value comes from `rules.json` or the tool API. The model in a node sees only that node's prompt, so a node is the policy that is in force.

1. Write `design.json`: `{"rows": [{"rules": ["r1", "r2"], "mechanism": "structure|code|prompt", "where": "<a node, tool or hook of workflow.json>"}], "warnings": {}}`, covering every live rule. By `kind`: gate, limit and allowed_set rules, and every rule that names a number or a count, are `structure` or `code`, never `prompt`. A `wording` rule puts its `wording` into the workflow exactly as the brief has it. A prompt row names its node (or system_prompt).
2. Keep it small: at most 1000 lines, 4 to 8 nodes, at most 8 prompt-only rules per node. More rules than that: split the node by state, or settle them in code and show the model the conclusion.
3. Decisions that matter (the docs explain how):
   - numbers are flow, not wording: limits, windows, deadlines, amounts and every counter are computed and held in code, and transitions branch on them
   - interdependent rules are settled in code: one code node derives the situation (stage, allowed set, deadline, attempts left) as variables; the prompt shows these facts, never the interplay of rules
   - each conversation node's `task_message` is its role, the situation facts (`{{vars}}`) and the policy of that node only: what may and may not be done, what must be conveyed and before what. Context and policy, not a script. Rules that hold everywhere are a few lines in `system_prompt`
   - gate: a protected tool exists only in nodes reached through a transition on the bank's own answer
   - customer intent enters through `extraction_schema` enum slots and transitions on them. A tool the model calls reports facts the code needs; its name and arguments never state an outcome the code then decides
   - writes: a pre hook on a tool the model calls validates the request and blocks an invalid one by setting `config['url'] = ''` (the platform answers "Missing required field: url" and sends nothing); never raise. Only there (F14). A post hook records state and returns facts and what is now allowed or forbidden, not a sentence to speak. `maxRetries` 0
   - failed calls: a service can answer with an error status (not found, a technical error, a timeout). That is an answer with a meaning, not a crash: read in the documents what each error of each service means and where the call goes then (say it plainly, ask again, try again, hand over). The platform counts it in `<tool>_failure_count` and keeps the status in `<tool>_response.status_code`; transitions branch on those. A read may be tried again a fixed number of times, counted in code (`attempts_left`), then the flow gives up the way the documents say; a call that changes something is never repeated automatically. A post hook turns the raw answer into plain facts for the model (`call_ok: no`, `error: <code>`, `attempts_left: N`, `next: ...`) so it never reads an error text aloud and never says something was done when the call failed (W9)
   - optional actions (notes, a transfer, a callback) are tools of one conversation node (W1)
   - a counter or gate that decides an outcome rests on the bank's own answers, the engine's `_failure_count`, `{{node.total_turns}}`, or an explicit tool call by the model with a closed set of values. An extraction slot is re-read from the last messages every turn: use it to fork routing, with an "unclear, stay" default, never as the count of what the customer did
   - customers ramble, go off topic, ask a question back, speak in pieces. A turn that does not advance the step changes no state and counts for nothing: answer in one sentence and ask the pending question again, shorter. Show the pending question as a fact (`pending: date of birth`) so the model returns to it. A step is closed by the bank's answer, an explicit refusal, or a turn cap that first tries once more or escalates (F11, W8), never by a rambling reply
   - an action allowed once (offer the support team, one sympathy sentence, one attempt per product) is one node that is left after it. Later nodes do not carry its instruction, and the situation facts say it was done (`support_offered: yes`). Use `on_enter_first_entry_only`, not a prompt rule
   - a rule that limits what the agent may offer (attempts, offers, asks): code computes the allowed set and what is left, the prompt shows it as a constraint ("allowed: ...; nothing else"), a transition ends the stage when none is left
   - language: every customer-facing sentence (system_prompt, task_message, fixed lines, farewell) is in the language of the documents. Code builds dates, amounts and currency names as text in that language (month and weekday names, number formatting); the model is never asked to format them. Dates are decided from the call's own clock variable when the case gives one (e.g. `now`), never the system clock
   - one lookup, then the facts: when the call starts from a variable (a customer number the caller never says), a passthrough node calls the lookup service and puts the answer in variables before the first sentence
   - close: the lifecycle `end_of_call` close tool, outcome and reason from `vars`; hang up with `end_call`
   - a read-back or confirmation shows what the customer just said. A value the customer gave and the code did not capture is asked for again; it is never replaced by an earlier value or a default
4. The loop: after every change to `workflow.json` run `python3 tools/check_workflow.py` (format rules, design, and a platform dry run). Fix every FAIL, run it again, until it prints READY. A WARN is a reason to look: fix it, or put one line under `warnings` in `design.json` saying why it stays. Then `python3 tools/publish.py workflow.json`, and `python3 tools/practice.py chat`: three live customer turns that show each reply. A missing, slow or wrong opening is a fix now, not after a full round; if even a stripped-down workflow does not answer, the platform is down: wait and run it again. The phase gate runs the same checks and a workflow is not tested before it passes them.

Done when check_workflow says READY, publish shows no READBACK line, the chat check is ok, and design.json is complete.
