# Phase 0: read the brief

`cat inputs.json` names the brief and the tool API, both under `input/`. The brief can have any name and any form: specification, mail, memo, notes, transcript. These two files and `docs/` are the only truth; use nothing from memory.

If `inputs.json` says `"mode": "final"`, the input is a case folder of documents (any language, Turkish for the final). **Open `input/digest.md` first**: code made it. It lists the documents newest first (read in that order; a newer document wins where they disagree), the lines of `corpus.md` that change or correct earlier text, the points left open, and the quoted wording. Meeting transcripts are shortened to their substance (the original is in `input/original/`). Use the digest to find what supersedes what before you write a rule. `input/corpus.md` holds the text of every document in reading order (BRIEF.md first, README.md says what each is), the originals are in `input/original/`, `tools` is the machine-readable service contract if there is one (otherwise it is one of the documents), and `base_url` is the mock the tools call: every tool URL is `base_url` plus the contract's path. Files listed under `data` (large tables of records, such as the bank's test customers) are not in the corpus: open the original and look up the customers you need. Documents listed under `visual` (drawings, images, PDFs) you must look at with the Read tool, even when their text is in the corpus: a flow drawing's text lists the boxes and loses the arrows, and the arrows are the rules (which question comes first, what each answer leads to). Turn every decision and branch of a drawing into rules; a rule taken from one has `source` (the file name) and a `note` saying what the drawing shows, instead of a verbatim quote. A later announcement or Q&A answer that changes a rule supersedes it (`refs`). Write every customer-facing sentence, and every `wording` rule, in the language of the documents.

**Time box (the harness tells you the minutes; the whole phase is about a quarter of the build):** read the newest version of each document completely and older versions only where the newest is silent; write rules per decision, limit, order, wording and per meaning of a service answer, not per sentence (about 60 to 100 rules for a long folder); generate `rules.json`, `topics.json` and `expectations.json` with a script in one go and do not polish. Topics (twelve at most): the case's example scenarios first (they are what is scored: the hidden customers are other customers of the same types), then for each type a variant on a different test customer whose data differs (another number of cards, an error answer, a missing block, a slow answer, a shared record), then one topic for every unusual data situation the test-data notes list. The workflow must work for the situation, not for the example.

1. Read the tool API completely: operations, fields, allowed values, which operations write.
2. Read the brief completely and in order, 150 lines at a time, to its last line. Searching for keywords is not reading.
3. Write `rules.json`: `{"brief_lines": N, "rules": [], "unused": {}, "skipped_lines": {}, "open_questions": []}`. One rule per atomic obligation, prohibition, permission, definition or table row, with:
   - `id`, `quote` (verbatim from the brief), `stage`, optional `note` and `refs`
   - `class`: gate (must never happen unless a condition holds), calc (a derived value), state (counters, once-only, per item), speech, flow (reaction to the customer), outcome (how the call closes)
   - `status`: decided, proposed, rejected, example, superseded, unresolved
   - `kind`, how the rule will be enforced: gate (order, a condition before an action), limit (a number, count or derived value), allowed_set (what may or may not be offered or done), wording (exact words the brief mandates: add `wording`, verbatim), content (facts that must be conveyed), style (tone, manner)
   - `applies`: the situation in which it is in force, in plain words; `depends_on`: ids of rules it overrides or limits
4. Mails, memos, notes: a hedge or a question is `proposed`. A later explicit amendment marks the earlier rule `superseded` (`refs`). Conflicts nothing resolves are `unresolved`: build the stricter reading and list it in `open_questions`.
5. Run `python3 tools/check_rules.py`. Fix every FAIL. Answer every WARN with a rule, or an `unused` / `skipped_lines` entry with a reason. In a case folder the documents are long and mostly talk: read all of them once, in large pieces, and write rules for what governs the call (decisions, limits, order, wording, what the services return and what each answer means); the newest decision wins over an older document and the older rule is `superseded`. Leave about two thirds of the time for the workflow and the tests.
6. Dev mode: `topics.json` lists the practice customers: what each one does, not what the bank must show. Final mode: write `topics.json` yourself from the bank's test customers and example conversations: a list of `{"id", "title", "script", "variables"}`, one per kind of call (identity, payment, dispute, refusal, a relative answering, a tool failing, several accounts: whatever the documents show), `script` = who the customer is and what they do on the call, in the documents' language, with the facts the call needs (including wrong answers where the call has them); `variables` = what the call starts with (the customer id the mock knows, and anything the workflow reads); Pick the topics' customers from the bank's own test customers, so the mock answers them. Every kind of call in the example conversations is a topic. Each product has the id the bank uses (`p1`, `p2`, ...); use it as `product_id`. For each, work out from `rules.json` alone what the call must leave in the bank and say, and write `expectations.json`: `{"<topic id>": {...}}`. Practice bank: `outcome`, `reason`, `promises` [{product_id, amount, date}], `notes`, `callbacks`, `transfers`. A mock: `calls` [{"tool", "args": {only the arguments that matter}}] and `forbidden_calls` [tool names], where a tool is named by the last part of its path in the contract (`.../v1/orders.get` is `orders.get`) and the arguments are the fields of the request's `data`. They are read from the platform's call log. Both: `must_state`, `must_not`, `rules` [ids]. Dates and amounts come from the brief's calendar and tables applied to that customer's products and `now`. If a rule does not settle an expectation, the rule is missing or wrong: fix `rules.json`, not the guess.
7. `python3 tools/check_expectations.py`.

Done when `check_rules` and `check_expectations` say ok.
